## 1. Что это за проект

**minskline.by** — лендинг + виджет онлайн-бронирования маршрутки
**Минск ⇄ Бобруйск**. Посетитель выбирает направление, дату, рейс, остановки,
количество мест, вводит имя и телефон, подтверждает бронь SMS-кодом.

- Живой сайт: <https://minskline.by/>
- Фирменный стиль: синий/фиолетовый градиент, жёлтый акцент, шрифт Open Sans.
- Валюта BYN. Есть блок «Мои поездки» (отмена брони по коду из СМС).
- Аудитория — русскоязычная, Белась. Язык вёрстки и код-комментариев: русский.

### Не путать

Внешний API бронирования живёт на **другом** домене — `minsk-bobruisk.by`.
Это не тот же сервер и не наш код. Фронт только ходит к нему за данными.

Проект **`F:\ML\nav\`** — чужой по смыслу (внутренний комплекс инструментов
на `ddt.by/nav`, свой код, свой API, своя защита). **Общего кода с
лендингом не имеет**, вынесен в отдельную папку. Подробности — в разделе 3.

## 5. Порядок загрузки — критично понимать

```
core/head.php
  ├─ <link> bootstrap.css  ─┐
  ├─ <link> styles.css      │ render-blocking, намеренно:
  ├─ <link> app.css         │ рисуют navbar + hero
  ├─ <link> icons-2026.css  │
  └─ <link> booking-2026.css┘  ← ПОСЛЕДНИМ, перекрывает легаси
  ├─ <script defer> vue.min.js
  └─ <script defer> axios.js

index.php (конец <body>)
  └─ <script> ...DOMContentLoaded → Vue.directive(...) → new Vue({el:'#apps'}) ... </script>

js/booking-2026.js  ← <script defer>, подключён ДО инлайнового, но defer'ы
                       выполняются в порядке подключения, поэтому он идёт
                       после разбора DOM
```

### ГЛАВНОЕ ПРАВИЛО ПРОЕКТА

`defer`-скрипты выполняются **после** разбора всего HTML, но инлайновый
скрипт в конце `<body>` выполняется **во время** разбора — раньше них.

Поэтому **всё**, что обращается к `Vue` или `axios` из инлайнового скрипта,
обязано лежать внутри `DOMContentLoaded`. Нарушение этого правила молча
(or с `ReferenceError`) убивает всё бронирование — см. п. 9.1.

## 6. API

Base: `https://minsk-bobruisk.by/cp/api/v1/ap/`

| Вызов | Когда | Ответ |
|---|---|---|
| `citya` | `created()` | список направлений «откуда» |
| `cityb?id=` | смена `city_a` | список направлений «куда» |
| `price` | `created()` | матрица цен |
| `reis?citya=&cityb=&date=` | смена даты | рейсы на дату |
| `stops?id=` | смена рейса | остановки начала/конца |
| `smsin?...` | «получить код» | отправка SMS |
| `bron` (POST) | подтверждение кода | сама бронь |
| `get-travel?number=&code=` | блок «Мои поездки» | список броней |
| `otm-travel?id=` | отмена брони | отмена |

Все ответы имеют ключ `responce` (`0` — ошибка + `message`, `1` — успех).
Это не HTTP-код: при ошибке бизнес-логики HTTP может быть 200.

**Внешний API может быть недоступен** (CORS, сеть). Код обязан это переживать:
у каждого `axios.get` есть `.catch` с `notify(...)`, `priceBron()` возвращается
на `null` вместо `throw`. Не добавляй вызовов без `.catch`.

## 7. Деплой и резервные копии

**Деплой ручной, со стороны пользователя**: он перетаскивает папку на
https://minskline.by/ (панель хостинга). У меня нет доступа, git нет,
автоматической выкладки нет.

### Обязательный шаг при каждой выкладке

Поднять `$asset_v` в `core/head.php:9`:

```php

```

Без этого браузер продолжит отдавать старые файлы из кэша. Ровно так уже
«потерялась» починка маски телефона: файл на сервере новый, а страница
показывала старое поведение. Сейчас: **`20260929-17`**.

Поднимать **только** если менялись `css/*` или `js/*`. Правка одного
`index.php` версию не требует — он и так отдаётся свежим.

### Резервные копии

Копия кладётся **в `F:\ML\`, не в папку проекта**. Причины: деплой
перетаскивает папку целиком, и zip внутри уехал бы на сервер; кроме того,
каждая следующая копия включала бы предыдущую (550 КБ → 1.1 МБ → 2.2 МБ).

**Имя файла:** `back_ДД_ММ_ЧЧММ.zip` — дата и время создания, по нему же
копии сортируются по возрастанию.

```powershell
$stamp = Get-Date -Format 'dd_MM_HHmm'
$zip = "F:\ML\back_$stamp.zip"
Add-Type -AssemblyName System.IO.Compression.FileSystem
if (Test-Path $zip) { Remove-Item $zip -Force }
[System.IO.Compression.ZipFile]::CreateFromDirectory('F:\ML\minskline.by', $zip, [System.IO.Compression.CompressionLevel]::Optimal, $true)
```

> Месяц (`ММ`) добавлен сверх исходного «число месяца + время»:
> без него сортировка врёт круглый год — `back_01_1015` (1 октября)
> встал бы раньше `back_29_0930` (29 сентября), хотя создан позже.
> Убрать легко, если не нужен.

## 9. ⚠️ Ловушки (здесь ломали сайт)

Это не теория. Каждый пункт — реально случившаяся поломка.

### 9.1 `Vue is not defined` — директива вне DOMContentLoaded

`Vue.directive('click-outside', ...)` стояло **снаружи** обработчика
`DOMContentLoaded`. Инлайновый скрипт выполняется во время разбора, до
`defer`ред `vue.min.js` → `ReferenceError: Vue is not defined` → всё
бронирование мертво.

**Правило:** в инлайновом скрипте `index.php` всё, что касается `Vue`/`axios`,
внутри `document.addEventListener('DOMContentLoaded', function () { ... })`.

**Как поймать:** `browser.console` с `level: 'error'`.

### 9.2 Лишняя `},` в объекте Vue-опций

Случайная `},` закрывала `methods: {` досрочно, и следующие методы
(`openDatepicker`, `prevMonth`, …) оказывались на верхнем уровне объекта
опций. Ошибка: `SyntaxError: missing ) after argument list`. Приложение
не поднимается вообще.

**Как поймать:**

```js
var s = Array.from(document.querySelectorAll('script:not([src])'))
              .filter(x => x.textContent.indexOf('new Vue') !== -1)[0];
try { new Function(s.textContent); } catch (e) { console.log('SYNTAX', e.message); }
```

### 9.3 `null.length` в шаблоне

`refreshReis()` присваивает `this.date = null`. Шаблон делал
`date.length === 0` → `TypeError: Cannot read properties of null` на каждом
рендере, форма не рисуется.

**Правило:** `date` — это `'' | null | 'YYYY-MM-DD'`. Проверяй `!date`,
а не `date.length`.

### 9.4 Лишняя `}` в CSS молча выбрасывает следующее правило

`css/booking-2026.css`, после `@media (forced-colors: active)` стояла
**вторая** закрывающая скобка. Браузер в режиме восстановления отбрасывал
следующее правило — `.bk-datepicker { position: relative }`. Правило
исчезло из CSSOM, и календарь позиционировался относительно `.bk-card`
(всей формы) вместо поля ввода: открывался на ~1500 px ниже, за экраном.

**Ни одной ошибки в консоли.** Выглядит как «CSS не применился».

**Как поймать (после правок CSS):**

```js
fetch('css/booking-2026.css?bust=' + Date.now()).then(r => r.text()).then(t => {
  var d = 0, min = 0, inC = false, inS = null;
  for (var i = 0; i < t.length; i++) {
    var c = t[i], n = t[i+1];
    if (inC) { if (c === '*' && n === '/') { inC = false; i++; } continue; }
    if (inS) { if (c === inS) inS = null; continue; }
    if (c === '/' && n === '*') { inC = true; i++; continue; }
    if (c === '"' || c === "'") { inS = c; continue; }
    if (c === '{') d++; else if (c === '}') { d--; if (d < min) min = d; }
  }
  return { finalDepth: d, minDepth: min, balanced: d === 0 && min === 0 };
});
```

`balanced` должно быть `true`. Проверяй **после каждой** правки CSS.

Дополнительно: убедись, что правило реально попало в CSSOM —

```js
var el = document.querySelector('.bk-datepicker');
getComputedStyle(el).position   // ожидается 'relative'
```

### 9.5 `toISOString()` сдвигает дату на день

`new Date(2026, 8, 29)` — локальная полночь. `.toISOString()` переводит в
UTC; в Минске (UTC+3) это `2026-09-28T21:00Z` → строка `"2026-09-28"`.
Пользователь выбирает 29-е, а уезжает на рейс 28-го.

**Правило:** для YYYY-MM-DD использовать `toISODate(d)` из `index.php`
(собирает из локальных `getFullYear/getMonth/getDate`).

### 9.6 `js/booking-2026.js` работает ДО монтирования Vue

Файл `defer`red и выполняется раньше, чем Vue смонтирует `#apps`.
Ссылка на элемент, взятая на верхнем уровне файла, окажется на
**отсоединённом** узле (Vue пересоздаёт разметку при монтировании).

**Правило:** внутри виджета всё делегировать от `document` либо
перезапрашивать в момент вызова. Уже так сделано — не ломай.

### 9.7 Дубли `id` в разметке

Было два `<span id="bk-date-hint">` — подпись рендерилась дважды, и
`aria-describedby` ссылался не туда. Дубли `id` ломают и скринридеры.

**Как поймать:**

```js
var seen = {}, dup = [];
document.querySelectorAll('[id]').forEach(n => seen[n.id] ? dup.push(n.id) : seen[n.id] = 1);
Array.from(new Set(dup));
// должно быть []
```

### 9.8 `overflow-x: hidden` на body

Делает body.scroll-контейнером и **отвязывает документ от вьюпорта**:
`documentElement.scrollHeight` схлопывается в один экран, ломаются
`window.scrollTo`, scroll-spy и `position: sticky`. В `core/head.php`
используется `overflow-x: clip` — это намеренно, не менять на `hidden`.

### 9.9 Кэш ассетов

См. п. 7. Правка есть на диске, а на странице её нет — почти всегда значит
не поднятый `$asset_v`.

### 9.10 «Фон есть, но его не видно»

Так чинили шапку на десктопе. `background-color` был задан (`#f1f9fc`),
но hero под ним начинался с `#c5eaf9` — два соседних светло-голубых тона.
Границы не видно, элемент выглядит «наложенным» на фон.

Прежде чем менять `background-color`, сравнивать с тем, что под элементом:

```js
getComputedStyle(document.querySelector('.navbar')).backgroundColor
getComputedStyle(document.querySelector('.header')).backgroundImage
```

Смежный класс ошибок — **элементы встык**: соседние блоки без отступа
считаются «наложенными», хотя не пересекаются. Замерять зазор:

```js
Math.round(social.getBoundingClientRect().left - menu.getBoundingClientRect().right)
// 0 = вплотную
```

### 9.11 Специфичность `.top-nav-collapse`

При прокрутке скрипт (`js/booking-2026.js`, «Navbar shrink on scroll») вешает
на навбар `top-nav-collapse`. У `.navbar.top-nav-collapse` специфичность
(0-2-0) — выше, чем у `.navbar` (0-1-0), и `styles.css:1302` в нём снова
ставит `#f1f9fc`.

**Правило:** любое оформление шапки, которое не должно слететь при
прокрутке, объявлять сразу двумя селекторами:

```css
.navbar,
.navbar.top-nav-collapse { ... }
```

Проверять в обоих состояниях (`scrollY: 0` и `scrollY: 600`).

### 9.12 `v-click-outside` на самом календаре закрывает его же

Календарь открывался на долю секунды и сразу прятался; повторно — только
после перезагрузки страницы.

Директива висела на `.bk-calendar`:

```html
<div class="bk-calendar" v-if="showDatepicker" v-click-outside="closeDatepicker">
```

Но поле ввода — **сосед**, а не потомок календаря. Реальный клик идёт
`mousedown → focus → mouseup → click`, и `@focus="openDatepicker"` успевает
открыть календарь **до** того, как `click` дойдёт до `document`. За это время
Vue успевает отрендерить `.bk-calendar`, директива привяжет слушатель к
`document` — и тот же клик будет признан «внешним»
(`el.contains(input) === false`), потому что input не внутри календаря.
`closeDatepicker()` закрывает то, что только что открыли.

**Почему не воспроизводилось на синтетических событиях.** Распылённые подряд
`dispatchEvent(focus)` + `dispatchEvent(click)` не воспроизводят: между ними
нет границы задачи, микротаска Vue (`nextTick`) не успевает отрендерить
календарь, слушатель не успевает привязаться и клик его не застаёт. У
настоящего клика граница задачи есть — `focus` и `click` это разные события
браузера.

**Воспроизведение (обязательно с `await` между событиями):**

```js
input.focus();
await new Promise(r => requestAnimationFrame(r));   // граница задачи
input.dispatchEvent(new MouseEvent('click', { bubbles: true }));
// → showDatepicker уже false
```

**Правило:** `v-click-outside` вешать на элемент, который содержит и
триггер, и выпадающую панель. Здесь это `.bk-datepicker` — он оборачивает
и поле, и календарь:

```html
<div class="bk-datepicker" v-click-outside="closeDatepicker">
    <input @click="openDatepicker" @focus="openDatepicker">
    <div class="bk-calendar" v-if="showDatepicker"> ... </div>
</div>
```

Побочная выгода: у `.bk-datepicker` нет `v-if`, поэтому директива
привязывается один раз при монтировании, а не на каждое открытие. Проверено:
25 циклов открыть/закрыть — слушатель на `document` один, состояние чистое.

### 9.13 `inset-block: 0` от обёртки, а не от поля

Иконка календаря съезжала вниз на 9.4px — на глаз это читалось как
«некрасивый логотип», хотя с самим глифом всё было в порядке.

`.bk-datepicker-icon` — `position: absolute; inset-block: 0`, а позиционирующим
предком был `.bk-datepicker`. Внутри него не только поле, но и подпись
`.bk-hint`, поэтому иконка растягивалась на всю обёртку:

| | было | стало |
|---|---|---|
| высота обёртки | 70.8px | 52px |
| высота поля | 52px | 52px |
| высота иконки | 70.8px | 52px |
| смещение центра от центра поля | **+9.4px** | **0** |

Девять с половиной пикселей — ровно половина высоты подписи (18.8px / 2).

**Правило:** элемент, который должен быть отцентрован по **конкретному**
блоку, нужно позиционировать от обёртки, равной этому блоку, а не от
внешнего контейнера, в котором лежит ещё что-то. Вложенность сама по себе
не задаёт границу.

```html
<div class="bk-datepicker">              <!-- содержит поле + подпись + календарь -->
  <div class="bk-datepicker-control">    <!-- только поле и иконка -->
    <input ...>
    <span class="bk-datepicker-icon"></span>
  </div>
  <span class="bk-hint">…</span>
  <div class="bk-calendar" v-if="showDatepicker">…</div>
</div>
```

```css
.bk-datepicker-control { position: relative; display: flex; }
```

Так центровка держится при любой высоте поля, а не при текущей.
Селектор `input:focus + .bk-datepicker-icon` продолжает работать: внутри
`.bk-datepicker-control` поле и иконка остались соседями.

### 9.14 `justify-content: center` без `flex: 0` у потомка

Центрирование карточек не сработало с первого раза, хотя `display: flex`,
`flex-direction: column` и `justify-content: center` в CSSOM были, а
вычисленные стили совпадали с заданными.

Причина — bootstrap: `.card-body { flex: 1 1 auto }`. Потомок с `flex-grow: 1`
забирает всю свободную высоту сам, и на `justify-content` её не остаётся.
Выглядело это как «центровка не работает»: блок прижимался к верху, лишнее
уезжало под текст (замерено 18px сверху / 38px снизу при высоте карточки 174).

**Правило:** чтобы центрировать содержимое через `justify-content`, все
потомки должны быть по своему размеру (`flex: 0 0 auto`). Иначе центрует
тот, кто растёт, а не контейнер. Проверять
`getComputedStyle(child).flexGrow` — должно быть `0`.

Отдельно: `display: block` в `#features .card` стоял не просто так — он
сбрасывал `inline-block` темы в медиазапросе. Заменять его на `display: flex`
безопасно: `#features .card` это (1,1,0) и перебивает `.cards-1 .card` (0,2,0),
то есть исходная причина сброса сохраняется.

### 9.15 `min-height` на flex-секции создаёт пустое поле

Пользователь жаловался на «раздутое белое поле» вокруг карточек. Отступы
секции были в норме (24px), а центровка содержимого — в норме. Поле раздувал
`min-height: 400px` на `#features`:

```css
#features.cards-1 {
  display: flex;
  justify-content: center;   /* центрирует внутри 400px */
  min-height: 400px;         /* ← источник пустоты */
}
```

Содержимое — 162px. Секция — 400px. Flex разносил ряд карточек, оставляя
**119px белого сверху и 119px снизу**. На десктопе это и есть «белое поле».

**Правило:** `min-height` на flex-контейнере с `justify-content: center` —
это заявка на пустое поле. Высота flex-контейнера должна идти от содержимого
и отступов. Если блок нужно сделать выше, добавлять `padding`, а не
`min-height`, иначе центровка сама разнесёт содержимое по краям.

Проверять: `getComputedStyle(sec).height` против суммы
`высота содержимого + paddingTop + paddingBottom`. Разница сверх padding —
незаполненная высота.

### 9.16 Соседние секции с прозрачным фоном сливаются в одно поле

Внешне карточки не были отцентрованы, хотя замеры говорили обратное
(25/25 по вертикали, 32/32 по горизонтали, дельта 0 на ширинах 1060–1920).
Смещён был не блок, а его граница: секция бронирования над блоком
преимуществ имеет `background: transparent` на белом `body`, и границы
секций совпадают вплотную (`featuresTop === prevBottom`). Два белых поля
сливались в одно, и до верха «белого блока» визуально было ~190px вместо 25.

**Правило:** перед тем как искать ошибку центровки, проверить, отличается
ли фон секции от фона соседей. Прозрачная секция на белом body не имеет
собственной границы — её не видно, и любая центровка внутри неё читается
неверно. Лечится собственным тоном фона, а не сдвигом отступов.

Проверять:

```js
getComputedStyle(sec).backgroundColor          // не transparent
prevSectionRect.bottom === secRect.top         // нет зазора
```

Смежный случай: соседняя секция задаёт фон **карточек** (`#pricing` идёт
сразу следом и красит фон фотографией), поэтому тонировать надо аккуратно
и держать палитру в одном тоне с карточками.

### 9.17 «Полоса» между блоками — это три слагаемых отступов

После тонировки блока преимуществ осталась белая полоса между ним и
карточкой бронирования. Она не была одним отступом — её складывали три,
замерено ровно 190px:

| источник | значение |
|---|---|
| `.reservation_form` padding-bottom | 77.75px |
| `.reservation_form` margin-bottom | 40px |
| `.basic-2.bk-section` padding-bottom | 72px |
| **итого** | **190px** |

Секция бронирования прозрачна на белом body, поэтому все три рисуются
белым и неотличимы друг от друга — выглядит как одна «полоса».

**Правило:** убирать «полосу» между блоками — обнулять **все**
слагаемые, а не подбирать отрицательный margin. Отрицательный margin
лечит симптом (190px сдвигом вверх) и ломается, как только любое из трёх
значений изменится.

Отдельно: `padding-bottom: clamp(2.5rem, 1.5rem + 5vw, 5.5rem)` даёт
77.75px на 1075px — визуально «неизвестный» отступ. Чинить его правильнее
в том же правиле, где он объявлен (`padding: ... 0 0`), а не конкурирующим
правилом ниже по файлу: при равной специфичности побеждает последнее, и
первая попытка молча не сработала (осталось 78px).

Проверять разбивку полосы:

```js
// пройти вниз от нижнего края карточки и сложить отступы до верхнего края
// следующего блока; сумма должна совпасть с измеренной «полосой»
```

### 9.18 `position: fixed` не режется overflow предков

Пользователь: на телефоне при сдвиге влево сайт уезжает за экран и
показывается белое поле.

Виновник — закрытая панель мобильного меню. В теме `styles.css:470` у неё
`position: fixed; left: 100%` и только `visibility: hidden`. Элемент
остаётся в раскладке, а `overflow-x: clip` на `html`/`body`
(`core/head.php`) её **не режет**: фиксированные элементы не обрезаются
overflow предков. Замерено в iframe 360px:

| | |
|---|---|
| вьюпорт | 345px |
| `documentElement.scrollWidth` | **690px** (ровно вдвое) |
| `body.scrollWidth` | 345px (тело чистое) |

По этой области телефон и панорамировался.

**Правило:** `overflow: hidden/clip` у предка **не** спасает от вылезающего
`position: fixed` потомка. Чинить у самого потомка: убрать из раскладки
(`display: none`) либо спрятать внутрь контейнера, который его обрежет.

Отдельно: `overflow-x: hidden` на `html` не просто не помогает, а **ухудшает**
(замерено 1035px вместо 690px) — ровно то, о чём предупреждает комментарий
в `core/head.php`. `clip` там не случаен.

### 9.19 Комментарий в JS может описывать несуществующее состояние

`js/booking-2026.js:332` утверждает: «панель display:none пока закрыта»,
и на этом основании читает фокус до снятия класса. Такого состояния в
стилях **не было** — только `visibility: hidden`. То есть код опирался на
баг, который никто не заметил, потому что и `left: 100%` давал overflow.

**Правило:** при чтении чужого кода как документации сверять каждое
утверждение с CSSOM, а не принимать на веру. Здесь исправление
`display: none` не просто чинит прокрутку — оно приводит страницу в
состояние, о котором код и думал.

### 9.20 Проверка мобильной вёрстки без телефона

Эмуляции вьюпорта в инструментах нет. Работает **iframe шириной 360px**:
медиазапросы в нём отрабатывают по-настоящему, и можно мерить
`contentDocument`.

```js
var f = document.createElement('iframe');
f.style.cssText = 'position:fixed;top:0;left:0;width:360px;height:640px;border:0;visibility:hidden';
f.src = '/_preview.html?probe=' + Date.now();
document.body.appendChild(f);
// ждать d.readyState === 'complete' и d.getElementById('apps').__vue__
var de = f.contentDocument.documentElement;
de.scrollWidth;            // должен быть <= clientWidth
```

Пре-сервер однопоточный: страница и её ассеты грузятся последовательно,
поэтому ждать надо polling'ом, а не фиксированной паузой. И не забыть
удалить iframe — он остаётся в DOM.

### 9.21 `justify-self` не работает в блочном родителе

Значок «МинскЛайн — официальный перевозчик» стоял на 87px левее центра
блока заголовка. Замерено: колонка текста и h1 занимают 65…595 (центр 330),
значок — 65…420 (центр 243).

Две причины складывались:

1. `display: inline-flex` внутри блочного `.text-container` с
   `text-align: start` — инлайн-бокс прижимался к левому краю.
2. `justify-self: start` рядом с ним был **мёртвым**: свойство действует
   только на грид- и флекс-элементы, а `.text-container` — `display: block`.

**Правило:** чтобы отцентрировать одиночный инлайн-элемент, `justify-self`
не поможет — нужен блочный уровень: `display: flex` (или `block`) +
`width: fit-content` + `margin-inline: auto`. Внутренняя раскладка при этом
сохраняется, потому что `flex-direction` по умолчанию `row`.

Перед правкой стоит замерить центры, а не смотреть на глаз:

```js
var c = function (el) { var r = el.getBoundingClientRect();
                        return Math.round((r.left + r.right) / 2); };
c(badge) - c(h1);   // должно быть 0
```

### 9.22 `align-items: center` ломает многстрочную подпись с маркером

Подпись «Номер телефона в международном формате:» на телефоне
переносится на две строки. `.bk-label` — это `display: flex` с
`align-items: center`, и красная звёздочка обязательности вставала
**посередине между строками**: отступ от верха текста 12px вместо 3px.

**Правило:** в флекс-строке, где items — текстовые узлы разной длины (в
том числе переносящиеся), выравнивать по `baseline`, а не по `center`.
`center` центрует каждый item по своей оси, и короткий item (звёздочка,
иконка, счётчик) уезжает в середину длинного.

Проверять на узкой ширине — на десктопе подпись влезает в одну строку и
проблемы не видно совсем:

```js
// 1. снять высоту label и line-height, посчитать строки
Math.round(labelRect.height / (parseFloat(fs) * parseFloat(lh)));
// 2. сравнить верх маркера с верхом текста (Range по текстовому узлу)
reqRect.top - textRangeRect.top;   // 3px = ок, 12px = съехало
```

### 9.23 `100vw` не учитывает полосу прокрутки

Панель календаря получила ширину `min(20rem, calc(100vw - 2rem))` и на
мобильном уезжала за правый край вьюпорта на 6px.

`100vw` — это ширина **включая** вертикальную полосу прокрутки: в iframe
360px `100vw` = 360, а `clientWidth` = 345. Панель привязана к левому краю
**поля** (31px), а не вьюпорта, поэтому «ширина вьюпорта минус отступ»
считается не от того края.

**Правило:** поплавок, позиционируемый относительно элемента, ограничивать
шириной **этого элемента** (`100%`), а не вьюпортом. Только тогда граница
верна при любой полосе прокрутки, любом отступе поля и любом положении.
`100vw` годится только для полноэкранных оверлеев, начинающихся от края.

Проверять, глядя именно на `clientWidth`, а не на ширину окна:

```js
Math.round(panel.getBoundingClientRect().right - document.documentElement.clientWidth);
// отрицательное = есть запас
```

### 9.24 Хардкод цвета ломает тёмную тему

Первый вариант нового календаря задавал выбранный день как
`linear-gradient(135deg, #1d4ed8, #2563eb)`. В тёмной теме `--bk-brand`
становится `#60a5fa`, и зашитое значение осталось бы светлым синим пятном.

**Правило:** производные цвета собирать из токенов, а не зашивать:

```css
background: linear-gradient(135deg,
  var(--bk-brand),
  color-mix(in srgb, var(--bk-brand) 78%, #fff));
box-shadow: 0 2px 8px color-mix(in srgb, var(--bk-brand) 35%, transparent);
```

Так градиент и тень следуют за темой сами. Ловится поиском по хардкоду в
своём же файле: `css.indexOf('linear-gradient(135deg, #1d4ed8') === -1`.

### 9.25 Проверка на `!= null` пропускает пустую строку

Кнопка «Очистить» в календаре ставит `date = ''`, а вотчер `date` проверял
`this.date != null`. Пустая строка — не null, проверка проходила, и уходил
запрос расписания с датой «». Лишний и бессмысленный: расписание без даты
не существует. В превью он дополнительно падал по CORS и выглядел как
ошибка сайта.

**Правило:** для значений, где «пусто» означает «нет значения», проверять
правдивость, а не `!= null`. `''` и `null` — оба «пусто», и различать их
почти никогда не нужно:

```js
// было
if (this.city_b != null && this.date != null) { ... }
// стало
if (this.city_b != null && this.date) { ... }
```

`!= null` оправдан только там, где `0` и `''` — **валидные** значения
(идентификатор может быть 0, поле — непустой текст). Тогда пишут явно.

Проверять, подменив `axios.get` счётчиком запросов по интересующему
эндпоинту — иначе в консоли видно только след (CORS/сетевую ошибку), а не
причину:

```js
var calls = [], real = window.axios.get;
window.axios.get = function (u) { if (String(u).indexOf('reis?') !== -1) calls.push(u); return real.apply(this, arguments); };
// ... действие ...
window.axios.get = real;   // не забыть вернуть
```

### 9.27 «Пусто» значит две разные вещи: грузится или нет

`refreshReis()` не обнулял `reis`, и при смене маршрута старое расписание
висело на экране секунду-две вместе со своей ценой.

Но обнулить `reis` в лоб — хуже. В шаблоне три блока выбирают состояние по
`v-if="reis.length > 0"`, и первый из них в `v-else` показывает
**«Рейсов на эту дату нет — выберите другую дату»**. Обнулили `reis` — и на
секунду мелькнуло сообщение, которое неправда: рейсы не отсутствуют, они
ещё едут.

**Правило:** «список пуст» и «список грузится» — разные состояния, и их
надо различать флагом, а не пустым массивом. Иначе либо висит старое, либо
показывается неверный текст.

```js
// data
loadingReis: false,

// запрос
if (город и дата) {
  this.loadingReis = true;
  axios.get(...).then(...).catch(...);   // в обеих ветках loadingReis = false
} else {
  this.loadingReis = false;               // обязательно: запроса не будет
}
```

```html
<div v-if="reis.length > 0">…</div>
<div v-else-if="loadingReis" class="bk-skel bk-skel--ctl" aria-hidden="true"></div>
<div v-else class="bk-empty">Рейсов на эту дату нет…</div>
```

Ветка `else` в JS обязательна: если город не выбран, запрос не уйдёт, и без
неё скелетон горел бы вечно. На проекте скелетон `.bk-skel--ctl` уже был —
он использовался в двух других блоках, то есть заготовка была, не хватало
только флага.

Проверять обязательно **момент до ответа**, а не итог:

```js
vm.swapRoute();
await wait(50);
// здесь должно быть reis: 0, loadingReis: true, .bk-empty — 0 штук
```

### 9.28 Токены `--bk-*` живут только внутри `.reservation_form`

Новостной блок `.bk-news` стоит **вне** формы брони. Написанный на токенах
(`background: var(--bk-surface)`, `border-radius: var(--bk-r-lg)`), он
потерял оформление: правила были в CSSOM, а `getComputedStyle` отдавал
`background: rgba(0,0,0,0)` и `border-radius: 0px`.

Причина: переменные объявлены внутри `.reservation_form`
(`booking-2026.css:1224`), вне формы они не определены, и объявление
отбрасывается на computed-value time.

**Правило:** вне формы брони — литералы. Это уже зафиксировано в проекте,
см. комментарий у `.bk-store-btn` (строка 743) и у `.bk-skip`, где токен
использован с запасным значением `var(--bk-font-sans, "Open Sans", …)`.
Поднять токены на `:root` можно, но это меняет тему самой формы — не
стоит ради одного блока.

**Как поймать:** правило в CSSOM есть, а стиль не применился — значит
дело не в каскаде, а в значении:

```js
getComputedStyle(el).getPropertyValue('--bk-surface').trim() || '(нет)'
// пусто = элемент вне формы, токен недоступен
```

Ловится и обходом CSSOM за любым правилом, содержащим `var(--bk-` вне
`.reservation_form`.

### 9.31 `object-fit: cover` режет по узкой стороне — считать заранее

Пользователь прислал фото своего автобуса: 1280×590, пропорции **2.17**.
Слот в блоке новостей 4:3, то есть 1.33.

Интуиция подсказывает: «кадр шире слота, значит срежется высота». Это
неверно. `cover` вписывает изображение по **более узкой** стороне, а
обрезает **более широкую**. Здесь шире исходник → режется ширина: остаётся
590 × 1.33 = **787** из 1280 px, то есть 61%. И `object-position: center`
срезал бы симметрично — и слева, и справа, а справа в кадре пустой фон,
который резать как раз не нужно.

Из-за этого потерялись бы ровно те детали, ради которых фото и берётся:
логотип «МЛЛ», табло «БОБРУЙСК МИНСК», госномер 6702ТК.

**Правило:** пропорции фото известны заранее, поэтому обрезать надо
**самому файл**, а не полагаться на `cover`. Тогда `object-position`
не важен, а вёрстка не зависит от того, как браузер решит кропнуть.

```js
// ширина окна под нужное соотношение при полной высоте
var w = Math.round(590 * (4 / 3));   // 787
var x0 = 70;                          // сдвиг окна влево, к кузову
```

Сравнил три окна (4:3 / 3:2 / 16:9) на монтаже и взял 4:3 — попало
и в уже прописанный `aspect-ratio: 4 / 3`, и по кадру: автобус занял
всю ширину, пустого фона почти не осталось.

**Проверка, что кропа не будет** — сравнить пропорции файла и
отрисованного бокса:

```js
Math.abs(img.naturalWidth / img.naturalHeight
         - img.getBoundingClientRect().width / img.getBoundingClientRect().height) < 0.01
```

`width`/`height` в разметке обязаны совпадать с **файлом**, а не с
исходником: `787`×`590`, иначе до загрузки резервируется неверная высота
и карточка прыгает.

Отдельно: в этом проекте **картинки нигде не ссылаются через `?v=`** —
все 20 вхождений `images/…` в `index.php`, `core/head.php`,
`core/setting.php` идут как есть. Для этой картинки метка всё же
добавлена, см. 9.32.

### 9.32 `loading="lazy"` на картинке из грид-строки не срабатывает

Фото новости стояло с `loading="lazy"` и **никогда не загружалось**.
Выглядело как кеш, но кешем не было.

Ход разбора, который стоит повторить в похожем случае:

```js
// 1. элемент вообще грузится по сети?
new Image().src = url + '?probe=' + Date.now();   // -> OK 787x590

// 2. что происходит с элементом в DOM?
img.currentSrc          // -> ""  пусто, загрузка не начата
img.naturalWidth        // -> 0
img.getBoundingClientRect()  // -> 361x271, бокс правильный
```

Если файл по сети отдаётся, бокс правильный, а `currentSrc` пуст — браузер
просто не начал загрузку. Дальше проверка настоящей прокруткой, а не
`scrollIntoView`:

```js
// прокрутка ступенями + ожидание
// img проходит вьюпорт целиком: rectTop 906 -> -594
// currentSrc так и остался ""
```

Причина: высота элемента приходит из грид-строки (`.bk-news-media` внутри
`grid-template-columns`), и нативная отложенная загрузка на таком элементе
не стартует. Элементы преимуществ с `loading="lazy"` работают, но они выше
первого экрана.

**Что сделано:** `loading="lazy"` убран, `decoding="async"` оставлен.
71 КБ не стоят того, чтобы фото в новости молча не появилось. Проверено на
свежей загрузке без прокрутки: `naturalWidth` уже 787 на первом же замере.

**`?v=$asset_v` на картинке** — исключение из конвенции, и вот почему.
`.htaccess` отдаёт jpeg с `Cache-Control: immutable` на год:

```
ExpiresByType image/jpeg "access plus 1 year"
Header set Cache-Control "public, max-age=31536000, immutable"
```

Заглушка и это фото делят один URL. Без метки у того, кто открывал страницу
с заглушкой, осталась бы заглушка на год, и обычное обновление не помогло бы.
Метка `$asset_v` обнуляет кеш точно так же, как для css и js, — при замене
фото поднимать `$asset_v`.

### 9.26 «Очистить» должен сбрасывать зависимое состояние

Даже после починки запроса кнопка оставляла форму в противоречивом виде:
поле «Дата» пустое, а рядом стояли время отправления и цена **прежней**
даты. Пользователь ничего не выбрал — а форма показывает рейс.

`clearDate()` теперь обнуляет и dependents: `reis`, `idReis`, `idStopFrom`,
`idStopTo`, `idCityFrom`, `idCityTo`, `priceReis`.

**Правило:** «очистить» значит вернуть поле в начальное состояние, а не
только стереть его значение. Если готовой функции сброса нет — свобода
не выглядит подходящей: `refreshReis()` обнуляет ещё и `city_b`, то есть
смену направления, чего при очистке даты делать нельзя. Свой точечный
сброс дешевле и безопаснее.

Отдельно: `refreshReis()` **не** чистил `reis`, поэтому при смене
маршрута старое расписание висело на экране, пока не придёт новое.
Исправлено в сессии 16, см. кейс 9.27.

### Сессия 11 — убрана горизонтальная прокрутка на телефоне
