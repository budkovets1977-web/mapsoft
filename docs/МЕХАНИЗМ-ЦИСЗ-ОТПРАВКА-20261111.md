# Механизм отправки в ЦИСЗ: посещения пациента и дневники врача

**Версия: 6.00.60 · Источник: `src/service/app/med/cisz/` · Дата: 11.11.2026**

ЦИСЗ (Централизованная информационная система здравоохранения РБ, интегрированная
электронная медицинская карта — ИЭМК) обмен построен на **FHIR R4** поверх REST
(Keycloak OAuth2 / PKCE). Вся логика — на бэкенде PHP, фронтенд лишь вызывает
JSON-RPC-методы и показывает статусы.

---

## 1. Архитектура (3 слоя)

| Слой | Файл | Роль |
|---|---|---|
| **API + auth** | `api.php` | OAuth2 PKCE-авторизация, токены, ValueSet/словари, HTTP-обёртка |
| **Оркестратор** | `bundle.php` | Единая точка отправки: `switch ($entity)` → сборка FHIR-ресурсов |
| **Traits** | `traits/*.php` | Билдеры FHIR-ресурсов (Encounter, ServiceRequest, Observation…) |

`bundle.php` использует `use` всех 24 trait'ов (encounter, patient, practitioner,
organization, observation, serviceRequest, carePlan, procedure, diagnosticReport,
episodeOfCare, medicationOrder, questionnaireResponse, vaccination и т.д.).

---

## 2. Авторизация (PKCE)

1. Нет access_token → `checkAuthAndGetUrl()` строит URL на Keycloak
   `realms/iehr/auth` с `code_challenge` (S256) + `state` = ID сессии.
2. После редиректа приходит `code` → `getToken()` меняет его на `access_token`
   через `code_verifier` (`realms/iehr/token`).
3. Из JWT `access_token` вытаскиваются `organization_id`, `practitioner_id`,
   `department_ids` → хранятся в сессии (`cisz`).
4. Продление — `refreshToken()` (refresh_token / refresh_expires_in).
5. Токен хранится в сессии: `getSessionValue('cisz')`.

## 3. Точка входа отправки

Фронтенд вызывает JSON-RPC `med_cisz_bundle` (метод `send`/`createBundle`),
передавая `{ entity, visitPatientId, patientId }`. Ключевые сущности:

| entity | Что отправляется (switch в bundle.php) |
|---|---|
| `MedPatient` | регистрация пациента: PlaceOfCare, RelatedPerson, FamilyMemberHistory, Composition |
| `MedVisitPatient` | **посещение врача**: Encounter + Observation + QuestionnaireResponse + MedicationOrder + AllergyIntolerance + EpisodeOfTemporaryDisability + DeviceOrder + VaccinationRecommendation + Composition |
| `MedStatCard` | статталон: то же + cancel-заказы + направления |
| `MedInspect` | диспансерный осмотр: Encounter + CarePlan + направления на консультации |
| `MedLogHospital` / `MedDayHospital` | EpisodeOfCare (госпитализация/дневной стационар) |
| `MedHospitalRequest` | ServiceRequest (направление на госпитализацию) |
| `MedLogStudy` / `MedLogStudyLab` / `MedLogStudyImage` | функциональная/лабораторная/инструментальная диагностика |
| `MedProcedure`, `MedXRayStat`, `MedRadioIzotop*`, `MedAmbulOperation` | процедуры/операции/лучевая |

## 4. Сборка ресурсов (на примере посещения `MedVisitPatient`)

Порядок в `bundle.php`:
1. `loadVisitPatient()` — читает строку посещения из БД (htmData = JSON шаблона формы).
2. `createOrganization()` / `createPractitioner()` — организация и врач.
3. `createPatient()` — пациент (или получает существующий UUID).
4. `createEncounter()` — **Encounter** (визит): период, тип визита
   (`EncounterTypeOfVisit`), диагнозы через `createConditionLink`.
5. `createObservations()` — показатели: АД, рост, вес, ИМТ и др.
6. `createQuestionnaireResponses()` — анкеты (анамнез, привычки, гинекология…).
7. `createMedicationOrder()` — назначения лекарств.
8. `createAllergyIntolerance()`, `createEpisodeOfTemporaryDisability()`,
   `createDeviceOrder()`, `createVaccinationRecommendation()`.
9. `createComposition($id)` — **сборка Bundle** из всех ресурсов + отправка.

## 5. Отправка и статусы

- Каждый ресурс — объект `{ fullUrl, resource }`, складываются в Bundle.
- `doHttpMethodWithAuth()` шлёт на `{url}fhir/...` с Bearer-токеном.
- **Связь MМ↔ЦИСЗ**: `storeLinkUnique()` хранит пару (локальный PK ↔ FHIR UUID)
  в таблице линков; при повторе проверяется `getLinkEntityUUID` — повтор не дублирует.
- **Статус** — таблица истории (`history()`): PENDING → SENT/CANCELLED/FAILED.
  Панель ЦИСЗ показывает «Статус пациента в ЦИСЗ: Изменено».
- Отмена: `cancelBundleImport()` → `$cancel` на Bundle; `setRequestStatus()` —
  смена статуса направлений (`$set-status`).

## 6. Дневники врача (`MedLogSend`, `MedLogStudy`)

- `MedLogSend` — направление на консультацию (`ServiceRequestConsult`),
  связано с дневником (`createServiceRequest('MedLogSend')`).
- `MedLogStudy` — диагностика; статусное поле `send` рулит, какие ресурсы
  (serviceRequest/procedure/observation/diagnosticReport) уходят.
- `setRequestStatus($id,$status,'MedLogSend'|'MedLogStudy')` меняет статус
  направления (revoked/completed) через `$set-status`.
- Новое в 59/60: `serviceRequest/hospitalisation/importer.php` — импорт
  направлений на госпитализацию (вставка MedLog + диагнозов + CiszDocExtra).

## 7. Словари и справочники

- `api.php` содержит `ciszDictList` (~200 ValueSet-идентификаторов) и
  `updateDirectoriesCIZS()` — фоновая синхронизация справочников в
  `CiszResource` / `CiszResourceValue` (для маппинга локальных кодов на FHIR coding).
- Маппинг кода → FHIR: `getCodingStructure(valueSet, code)`, `getDisplayByCode()`.

## 8. Конфигурация

Настройки подключения (clientId, urlAuth, redirectUri, origin) — в `constant.php`
+ `readExtraSettings(db, SETTING_NAME)` (таблица настроек, имя константы
`med_cisz_constant::SETTING_NAME`). Сервер Keycloak — `urlAuth`, FHIR — `url`.
Подпись документов — внешний сервис `http://<ip>:8084/sign` (CMS, `encodeAndSign()`).

## Итог

Отправка в ЦИСЗ — это **синхронный FHIR-конвейер**: JSON-RPC `med_cisz_bundle.send`
→ `switch(entity)` → сборка цепочки FHIR-ресурсов через traits → Bundle + POST в
ИЭМК с Bearer-токеном → сохранение линков (локальный PK ↔ FHIR UUID) и истории
статусов. Посещение = Encounter (+Observation/Questionnaire/Medication/…), дневник =
ServiceRequest (+ Procedure/DiagnosticReport/Observation). Панель «ЦИСЗ» на карточке
пациента показывает локальный статус отправки из таблицы линков/истории.
